## Етап 0 — аудит і безпечна гілка

**Статус: виконано. Дані та схема БД не змінювалися.**

### Перевірений baseline

- Один modular FastAPI застосунок, один React/Vite застосунок і одна PostgreSQL БД.
- Alembic має послідовний additive ланцюг `0001–0011`.
- Реалізовані модулі: auth/users/roles, R&D, components/setups/tests/files,
  products/revisions/specification/technology/routes/firmware, orders/variants,
  procurement та production execution.
- У frontend уже є сторінки огляду, R&D, продукції, об'єднаний екран
  замовлень/виробництва, «Моя робота», пошук і адміністрування.
- Backend capability policy вже захищає предметні операції. У frontend
  capability-фільтрація застосована лише до адміністрування та частини дій;
  основні пункти меню ще доступні без узгодженого фільтра.
- Поточний UI використовує постійне бокове меню, англійські назви модулів і
  місцями пошкоджений UTF-8. Це головний обсяг етапу 1.

### Що вже існує і повторно використовується

| Контур | Наявна реалізація | Рішення |
|---|---|---|
| Доступ | `Role`, `UserRole`, `Capability`, backend service checks | Зберегти; меню та route guards читатимуть ті самі capabilities |
| Розробка | projects, branches, setups/configurations, tasks, tests, files | Зберегти маршрути та сторінки; згрупувати під «Розробка» |
| Продукція | Product, ProductRevision, revision BOM, technology, firmware, routes | Зберегти; у UI використовувати «Версія», «Специфікація», «Прошивки» |
| Замовлення | Customer, Order, OrderItem, OrderVariant, VariantDeviation | Зберегти; дати окремий маршрут `/orders` |
| Закупівлі | ProcurementRecord, ProcurementAllocation | Залишити вкладеною можливістю «Замовлень» |
| Виробництво | ProductionItem, StageExecution, StageEvent, checklist snapshots | Зберегти; дати окремий маршрут `/production` |
| Працівник | `/my-work`, QR/item route, backend eligibility | Зберегти як допоміжний перехід |
| Склад | Повного ledger немає | Показувати чесний стан «ще не реалізовано» без нульових залишків |

### Межі модулів після етапу 1

1. **Розробка** — наявний R&D контур.
2. **Продукція** — каталог моделей і виробничих версій.
3. **Замовлення** — планування, замовники, рядки, матеріальна потреба,
   погоджені заміни та закупівлі.
4. **Виробництво** — фактичні вироби/партії, операції, виконавці й прогрес.
5. **Склад** — явний майбутній модуль без вигаданих показників.

На етапі 1 `/orders` і `/production` можуть повторно використовувати наявний
компонент, оскільки функціональне розділення екранів належить етапу 2.
Старий `/production/orders/:id` має перенаправляти на `/orders/:id`.

### Модель комплектацій і майбутня міграція

- Наявний `OrderVariant` залишається поділом кількості конкретного замовлення.
- Постійна комплектація каталогу буде окремою `ProductVariant` між `Product`
  і `ProductRevision`: `Product → ProductVariant → ProductRevision`.
- Для чинних продуктів майбутня additive migration створить «Стандартну»
  комплектацію та прив'яже до неї наявні версії без зміни їх UUID.
- `ProductRevision.product_id` тимчасово лишиться для сумісності. Належність
  версії, комплектації та моделі контролюватимуть FK/constraints і service check.
- На етапах 0–1 схема продуктів і замовлень не змінюється.

### Права і сумісні URL

- `VIEW_RND_DASHBOARD` або чинний доступ учасника відкриває «Розробку»;
  прямі предметні запити й надалі перевіряє backend.
- `VIEW_ENGINEERING` відкриває «Продукцію».
- `VIEW_PRODUCTION`, `MANAGE_ORDERS` або `MANAGE_PROCUREMENT` відкриває
  «Замовлення»; `VIEW_PRODUCTION` відкриває «Виробництво» і «Моя робота».
- `ADMIN_USERS` відкриває користувачів і налаштування.
- Старі URL предметних сторінок R&D зберігаються. Старий URL картки замовлення
  `/production/orders/:id` лишається сумісним через redirect.

### Формули матеріалів, які не змінюються на етапах 0–1

- Потреба формується з immutable `MaterialRequirement` snapshot.
- Погоджена заміна переносить кількість зі стандартного компонента на заміну;
  вона не додає заміну поверх повної стандартної потреби.
- `ordered`, `in_transit`, `received` мають бути взаємовиключними станами
  покриття allocation. Фізична готовність відрізняється від очікуваного
  постачання.
- Виправлення обліку `RECEIVED` і блокування запуску належать етапу 5.

### Порядок наступних additive migrations

1. `ProductVariant` і backfill «Стандартна» — етап 3.
2. За потреби snapshots/поля нового екрана замовлення — етап 4.
3. Події отримання або інші поля фізичної готовності — лише з точними
   правилами етапу 5.
4. Повний warehouse ledger — відкладений етап 7.

### Ризики

- Пошкоджене кодування в UI може приховати неперекладені написи; етап 1
  перевіряє UTF-8 і браузерне відображення.
- Тимчасове повторне використання одного компонента для `/orders` та
  `/production` не повинно створити дві копії бізнес-логіки.
- Надмірне приховування меню може забрати доступ учасника до власного R&D;
  guards повинні враховувати чинну модель доступу, а не лише роль.
- Документи README/ARCHITECTURE/DATABASE/ROADMAP частково застаріли. Повне
  узгодження всіх історичних секцій лишається етапом 8.

## Етап 5 — правильні матеріали, отримання й запуск

**Статус: виконано.**

### Реалізовано

- Матеріальна зведена таблиця окремо показує «Отримано під замовлення»,
