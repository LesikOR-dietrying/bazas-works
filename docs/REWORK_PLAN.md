# BAZA — промпт для поетапного доопрацювання

Дата: 04.10.2026. Репозиторій: https://github.com/LesikOR-dietrying/bazas-works

Цей файл можна передати Codex у VS Code цілком. Він містить нові вимоги,
порядок задач і критерії завершення. Це доопрацювання існуючої BAZA зі збереженням
даних та історії. Завдання цього запуску — **етап 0 та етап 1**. Наступні етапи
виконувати окремо за моєю командою.

## Роль і мета

Ти працюєш як архітектор та розробник існуючої внутрішньої системи BAZA.
Перетвори наявні розрізнені екрани на зрозумілі робочі процеси інженера,
керівника, закупівельника та працівника виробництва.

Спочатку прочитай AGENTS.md, ARCHITECTURE.md, CODEX_PRODUCT_SPEC.md,
README.md, docs/DATABASE.md, docs/ROADMAP.md, docs/OPERATIONS.md і
docs/VERIFICATION.md. Перевір код: документація місцями застаріла.

Нові вимоги цього промпту уточнюють стару структуру з чотирьох модулів:
тепер основних розділів **п'ять**. Узгодь з ними документацію, не видаляючи
інші чинні вимоги й не оголошуючи незавершені можливості готовими.

Збережи один FastAPI застосунок, один React застосунок, PostgreSQL,
наявні UUID, файли, користувачів, ролі, результати тестів і міграції.
Не переписуй застосунок з нуля. Нові міграції — додаткові, з перевіркою
перенесення чинних записів. Не використовуй SQLite замість PostgreSQL.

## 1. Нова структура і мова

Увесь стандартний інтерфейс українською: меню, заголовки, вкладки, кнопки,
статуси, підказки, помилки, порожні стани, підтвердження, форми,
сповіщення, назви ролей, підписи графіків, друковані сторінки та QR-етикетки.

Основне меню:

1. **Розробка** — повна назва сторінки «Дослідження та розробка»;
   це колишній RND/R&D.
2. **Продукція**.
3. **Замовлення**.
4. **Виробництво**.
5. **Склад**.

Назва BAZA, назви виробників, моделей, артикулів, файлів, протоколів та
користувацькі записи зберігаються. Не перекладай внутрішні назви Python/TS,
API endpoints, таблиць, enum codes або machine identifiers лише заради UI.
Наприклад, код IN_PROGRESS залишається в API, а користувач бачить «У роботі».
У підписах використовуй «Специфікація» замість BOM, «Прошивки» замість
Firmware, «Чернетка» замість draft, «Версія» замість Revision,
«Передати в продукцію» замість promotion.

Створи спільні типізовані словники статусів і назв, щоб різні екрани
не перекладали однакові коди по-різному. Не показуй raw UUID або enum там,
де потрібна зрозуміла назва. Розрізняй омонімічні статуси різних сутностей.
Не встановлюй велику бібліотеку локалізації без обґрунтованої потреби.
Серверні domain errors українською; для помилок валідації форм — зрозумілі
українські повідомлення, без показу traceback/SQL чи технічного JSON.

«Головна», «Мої задачі», «Моя робота», «Пошук», «Користувачі» та
«Налаштування» — допоміжні переходи, а не додаткові основні модулі.
Натискання BAZA може відкривати огляд. «Моя робота» є зручним входом
у виробництво для працівника. Доступність пунктів залежить від ролей.
П'ять розділів — повна структура системи, а не вимога показувати всім усе.

## 2. Візуальний напрям за наданими прикладами

Перший приклад: щільна таблиця комплектуючих зі стовпцями, кількістю,
статусами, позначками і розгортанням замін під відповідним компонентом.
Другий приклад: верхнє меню виробничої системи Katana і таблиця замовлень,
де окремі колонки показують матеріали, виробництво та відвантаження.

Використай ці принципи без копіювання бренду, зайвих інтеграцій і чужих даних:

- Верхня горизонтальна панель з п'ятьма основними розділами, активним
  пунктом, пошуком та меню користувача. Не дублюй її постійним боковим меню.
- Під нею — вкладки конкретного модуля, короткий заголовок і потрібні дії.
- Світлий фон, компактні рядки, чіткі межі колонок, помірні відступи.
- Зелений/жовтий/червоний/сірий сигнал разом із текстом або іконкою:
  стан не можна передавати лише кольором.
- Таблиці з фільтрами, серверною пагінацією і зрозумілим сортуванням.
- Для великих таблиць — горизонтальне прокручування та читабельний
  перший ідентифікаційний стовпець; перевір довгі назви і багато записів.
- Чекбокс позначає вибір рядка або реальну дію чекліста, а не вигаданий
  «успіх». Масова дія доступна лише коли справді реалізована в API.
- На планшеті верхнє меню адаптується, робочі дії лишаються великими.
- Не додавай великі рекламні блоки, декоративні схеми та англійські
  «engineering workspace» написи над кожною робочою таблицею.

## 3. Межі відповідальності п'яти модулів

| Модуль | Що містить |
|---|---|
| Розробка | Проєкти, задачі, відповідальні, гілки вдосконалень, експериментальні конфігурації, випробування, вимірювання, результати, прошивки та файли |
| Продукція | Моделі виробів, постійні комплектації, їх версії, характеристики, специфікації, собівартість, техкарти, прошивки, маршрути й інструкції |
| Замовлення | Замовники, замовлення, рядки виробів, кількості, вибрані комплектації/версії, потреба в матеріалах, закупівлі та погоджені заміни |
| Виробництво | Черга виконання замовлень, фізичні вироби/партії, операції, виконавці, чеклісти, результати та фактичний прогрес |
| Склад | Окремий майбутній модуль фізичних залишків, рухів і резервування; зараз чесно показує стан реалізації |

Розділи «Замовлення» та «Виробництво» мають різні головні сторінки.
Замовлення планує, **що і скільки** потрібно виготовити. Виробництво
показує, **що фактично виконується, ким і на якому етапі**.
Закупівлі на цьому етапі — підрозділ «Замовлень», не шостий основний модуль.

## 4. Динамічна продукція зі збереженням історії

Розрізняй чотири поняття:

- **Модель виробу**: наприклад, «Дрон 15».
- **Комплектація виробу**: постійний іменований вид, наприклад,
  «Оптичний» або «Цифровий». Це різновиди, які можуть існувати одночасно.
- **Версія комплектації**: історія змін конкретного виду, наприклад,
  «Оптичний, версія 2». Вона має власні характеристики, специфікацію,
  техкарту, прошивки, маршрут та стан затвердження.
- **Заміна під замовлення**: виняток для конкретної кількості одиниць
  замовлення. Він не переписує стандартну комплектацію каталогу.

Наявні Product, ProductRevision, ProductRevisionBomItem, OrderItem,
OrderVariant і VariantDeviation є основою. OrderVariant — поділ кількості
рядка замовлення, а не каталог постійних видів продукції.

Для постійних комплектацій передбач окрему нормалізовану сутність
ProductVariant, якщо еквівалентної сутності немає в актуальному коді.
Не підмінюй її JSON-масивом усередині Product або назвою ProductRevision.
Зв'язок: Product → ProductVariant → ProductRevision. Для старих виробів
створи початкову комплектацію «Стандартна» і прив'яжи чинні версії,
зберігши їх UUID та зв'язки замовлень. ProductRevision.product_id можна
тимчасово зберегти для сумісності; контролюй належність версії та
комплектації одній моделі через FK/обмеження і сервісну перевірку.
Поточна затверджена версія визначається для кожної комплектації окремо.

Не додавай зайві дубльовані FK до OrderItem, якщо комплектацію можна
однозначно отримати через product_revision_id. Назви й коди, які мають
зберігатися історично, фіксуй разом із затвердженою версією; перейменування
моделі не повинно непомітно переписувати історичні документи.

Правила змін:

1. Чернетку версії можна редагувати.
2. Після затвердження склад і виробничі інструкції незмінні.
3. Постійна зміна: скопіювати версію в нову чернетку, змінити компоненти,
   перевірити, затвердити. Попередня версія лишається доступною в історії.
4. Зміна лише під замовлення: розділити його кількість, записати причину
   і заміну, погодити, за потреби додати результати повторного випробування.
5. Нове замовлення прив'язується до **точної затвердженої версії**.
   Після появи нової версії старе замовлення не оновлюється автоматично.
6. Непогоджена заміна не потрапляє в виробничу специфікацію.
7. На екрані заміни показуй старий/новий компонент, кількість, причину,
   автора, погоджувача та вплив на ціну/характеристики, якщо є реальні дані.
   За відсутності вимірювань показуй «Потрібна перевірка», а не вигаданий ефект.

## 5. Автоматичний склад замовлення

У створенні/редагуванні замовлення користувач вибирає:
**модель → комплектацію → затверджену версію → кількість**.
Каталог не є складом: вибір виробу з каталогу не доводить наявності матеріалів.

Одразу після вибору сервер повертає попередній склад: назви компонентів,
артикули, кількість на один виріб, кількість на замовлення, одиниці виміру
та погоджені альтернативи. При зміні кількості таблиця перераховується.
Ручний ввід необхідної кількості компонентів користувачем не потрібний.

Розрахунок: ефективний склад затвердженої версії плюс погоджені заміни,
помножений на кількість відповідної групи виробів. Остаточний розрахунок
і перевірка завжди на backend. Перегляд не повинен створювати або змінювати
записи. До підтвердження дозволений попередній розрахунок; при підтвердженні
фіксується виробнича потреба. Не змінюй snapshots запущених замовлень.

Приклад для перевірки: 100 виробів, по 4 мотори. Для 90 виробів стандартний
мотор, для 10 — погоджена заміна. Потреба: **360 стандартних + 40 інших**.
Не 400 + 40. Специфікація каталогу залишається незмінною.

Головна таблиця «Замовлення»:

| Номер | Дата | Замовник | Вироби/комплектації | Кількість | Строк | Матеріали | Виробництво | Відвантаження |
|---|---|---|---|---|---|---|---|---|

Матеріали та виробничий прогрес — розрахункові статуси, не ручні прапорці.
Суму показуй лише якщо є справжній розрахунок ціни замовлення. Собівартість
не прирівнюй до ціни продажу. Відвантаження поки позначай «Облік ще не
реалізований», якщо відповідного модуля немає; не виводь вигадані нулі/успіх.

Сторінка замовлення: «Огляд», «Вироби», «Комплектуючі», «Закупівлі»,
«Виробництво», «Відвантаження». Перехід у виробництво відкриває пов'язану
чергу виконання, не створює друге незалежне замовлення.

## 6. Матеріали, закупівлі та фізична готовність

Виправити знайдену помилку: orders/service.py → material_summary зараз
враховує ORDERED/PAID та IN_TRANSIT/CUSTOMS, але не RECEIVED. Тому після
отримання закупівлі нестача з'являється знову.

Окремо показуй «Потрібно», «Отримано під замовлення», «Замовлено»,
«У дорозі», «Не покрито закупівлею» та «Бракує для запуску».
Заплановане покриття і фізична готовність — різні показники.

На першому кроці повністю отримана ProcurementRecord покриває фактично
прив'язану до замовлення кількість через ProcurementAllocation. Отримання
не створює автоматично достовірний загальний складський залишок.
Кожна кількість враховується лише в одному поточному стані. ISSUE не
вважається гарантованим постачанням. Кількість алокацій не може перевищити
кількість закупівлі; один отриманий обсяг не покриває два замовлення двічі.

Не підмінюй відсутній склад нульовими «Доступно»/«Зарезервовано».
До появи справжнього складського обліку ці колонки приховай або покажи
«Облік ще не ведеться». Повний складський ledger у цьому плані не реалізується.
Часткові отримання не імітуй одним статусом RECEIVED: якщо їх додаєш,
потрібні події отримання з кількостями та окремі критерії перевірки.

Не сумуй штуки, метри й кілограми в один відсоток. Для загального стану
показуй число повністю забезпечених позицій із загальної кількості або
іншу чітко описану безрозмірну формулу. Фізично неготові матеріали не
повинні давати зелений статус «Готово до запуску».

За замовчуванням запуск цілого замовлення вимагає фізичної забезпеченості
всіх необхідних позицій. Правило перевіряє сервер. Частковий запуск —
окреме майбутнє правило з точними кількостями; не запускай неповну партію
мовчки. Уже запущені замовлення не скасовуй через нову перевірку.

## 7. Відомі прогалини, які також потрібно закрити

- ProductDetail.tsx: вкладки прошивок і маршруту зараз показують тільки
  «N записів». Потрібні самі записи, перегляд і дозволені дії редагування.
- ProductDetail.tsx та WorkerItemPage.tsx: блоки IMAGE/ANNOTATED_IMAGE
  виводяться як текст. Потрібний спільний renderer реального контенту.
- У картці виробу відсутній повний UI характеристик, собівартості,
  копіювання версії й передачі затвердженого результату розробки в продукцію.
- Доступ до основного меню майже не фільтрується за повноваженнями.
  Зберегти серверний захист і зробити відповідний до ролей UI.
- README, ARCHITECTURE, DATABASE та ROADMAP мають застарілі початкові
  статуси. Узгодити з кодом і реально виконаними перевірками.
- У README знайдено некоректно доданий хвіст із нульовими символами,
  а в старих частинах VERIFICATION є зіпсоване кодування. Виправити UTF-8,
  не вигадуючи нові результати історичних перевірок.
- Немає повноцінних дефектів, ремонту, відвантаження та складу.
  Це відкладені можливості, а не підстава показувати успішні стани.

## 8. Етапи роботи та задачі

### Етап 0 — аудит і підготовка безпечної гілки

- Перевір фактичні міграції, API, моделі та UI. Порівняй із цим промптом.
- Виконай git status, перевір remote origin і поточну гілку.
- Створи або продовж гілку `refactor/baza-uk-orders` від актуального
  погодженого baseline. Не перезаписуй незбережені зміни користувача.
- Додай цей план як docs/REWORK_PLAN.md і файл docs/REWORK_PROGRESS.md
  із задачами, критеріями та місцем для результатів кожного етапу.
- Зафіксуй модель комплектацій, старі посилання/redirects, права доступу,
  формули матеріалів і порядок додаткових міграцій.
- Розділи: вже існує; потрібно підключити UI; потрібне нове поле/таблиця;
  відкладено. Не створюй дублікати наявних сервісів і сутностей.

Готово: є перевірений план і відома початкова версія коду; дані не змінені.
Коміт: `docs: план доопрацювання BAZA`.

### Етап 1 — український інтерфейс і п'ять розділів

- Зроби верхнє меню з новою структурою; огляд — через BAZA.
- Створи маршрути для окремих «Замовлень» і «Виробництва»; тимчасово
  повторно використовуй чинні компоненти без дублювання бізнес-логіки.
- Збережи старі посилання: `/production/orders/:id` має вести на те саме
  замовлення через redirect або сумісний маршрут.
- Переклади всі стандартні написи, статуси та помилки; прибери англійські
  декоративні підзаголовки. Не виконуй глобальну заміну кодових ідентифікаторів.
- Винеси словники підписів. Прибери raw UUID в картці поточної версії.
- Додай capability-фільтрацію меню й зрозумілу сторінку відмови в доступі.
  Чинний доступ учасника до своїх проєктів не втрать.
- Адаптуй верхнє меню до вузьких екранів, збережи keyboard navigation.

Перевір: адміністратор бачить п'ять розділів; працівник — лише дозволені
переходи; старий URL замовлення працює; код статусу лишився той самий,
але його текст український. У цьому етапі не змінюй схему виробів/замовлень.
Коміт: `feat: український інтерфейс і п'ять основних розділів`.

**Після етапів 0–1 зроби push, звіт і зупинись. Решта — за окремою командою.**

### Етап 2 — відокремити замовлення від виробничого виконання

- Перенеси таблицю замовлень, замовників і закупівлі в «Замовлення».
- Створи головну «Виробництво»: активні замовлення, виконані/заплановані
  кількості по операціях, відповідальні, заблоковані етапи та перехід до виробу.
- Збережи єдині Order/ProductionItem/StageExecution та спільні API-сервіси.
- Не копіюй весь код ProductionPage в нову сторінку: виділи зрозумілі
  компоненти списку замовлень, закупівель і виконання.
- Фільтри/пошук/пагінація працюють із API, а не лише з першими 100 записами.

Перевір: замовлення видно в плануванні; після запуску те саме замовлення
видно у виконанні; працівник відкриває призначену операцію без зайвих форм.
Коміт: `refactor: окремі екрани замовлень і виробництва`.

### Етап 3 — комплектації продукції та повна картка версії

- Реалізуй модель постійних комплектацій і сумісний backfill.
- Каталог: модель, комплектації, чинна затверджена версія та стан.
- Картка: характеристики, специфікація, собівартість/валюта, файли,
  історія та зрозумілий вибір комплектації/версії на всіх вкладках.
- Додай «Створити комплектацію», «Скопіювати в нову версію»,
  «На перевірку», «Затвердити». Дії тільки за дозволами.
- Редактор специфікації: додавання, зміна і підтверджене видалення;
  затверджені версії незмінні також через прямий API-запит.
- Підключи передачу схваленого результату розробки до чернетки продукції,
  збережи посилання на джерело, характеристики й доступні докази.
- При передачі/копіюванні не загуби прошивки та технічні дані й не
  копіюй файли або вимірювання довільно: збережи коректні посилання/snapshots.
- Якщо немає цін компонентів — собівартість має стан «Не розраховано»
  або явно ручну оцінку. Автоматичний розрахунок не імітуй нулем.

Перевір на PostgreSQL: дві комплектації однієї моделі існують паралельно;
версія належить правильній комплектації; старі замовлення й UUID збережені;
копіювання версії не змінює джерело.
Коміт: `feat: комплектації та версії продукції`.

### Етап 4 — автоматична специфікація й новий екран замовлення

- Реалізуй вибір модель/комплектація/версія/кількість із попереднім
  серверним розрахунком комплектуючих без запису даних на перегляді.
- Підключи вже наявні механізми поділу кількості та погодження замін.
- Покажи змінені компоненти й альтернативи під відповідними рядками.
- Фіксуй точну затверджену версію та ефективну специфікацію замовлення.
- Побудуй таблицю і вкладки за описом розділу 5 цього промпту.
- Відображай строки та прострочення; приховуй недоступні дії за правами.
- Додай серверну перевірку актуальності чернетки перед підтвердженням,
  щоб два менеджери не перезаписували зміни мовчки.

Перевір: 100 виробів + одна наземна станція дають правильну потребу;
90/10 виробів із заміною моторів дають 360/40; після нової версії каталогу
старе замовлення зберігає склад; непогоджену заміну не можна запустити.
Коміт: `feat: замовлення зі складом із каталогу продукції`.

### Етап 5 — правильні матеріали, отримання й запуск

- Врахуй RECEIVED і відокрем фізичну готовність від очікуваного постачання.
- Виправ забезпечення з урахуванням алокацій, станів та одиниць виміру.
- Покажи «Отримано під замовлення», «Замовлено», «У дорозі» та два
  різні дефіцити. Не підставляй вигадані складські залишки.
- Після зміни закупівлі оновлюй також матеріали/огляд пов'язаного
  замовлення через коректну інвалідацію кешу, без ручного reload сторінки.
- Сервер блокує запуск при фізичному дефіциті і повертає перелік
  позицій, які потрібно забезпечити. Повторний запуск ідемпотентний.

Перевір: перехід «У дорозі» → «Отримано» не повертає нестачу;
отриманий обсяг не рахується також як замовлений/у дорозі;
одна закупівля не покриває два замовлення понад свою кількість;
метри й штуки не складаються в один показник; запуск без матеріалів
неможливий прямим API-запитом.
Коміт: `fix: матеріали й фізична готовність замовлень`.

### Етап 6 — техкарти, прошивки та маршрути

- Заміни «N записів» повними списками прошивок і маршруту, з версіями,
  описами, файлами, порядком операцій, ролями та залежностями.
- Додай редагування визначення лише в чернетках; за відсутності потрібного
  endpoint доповни наявний модуль замість client-only збереження.
- Зроби спільний renderer TEXT/IMAGE/WARNING/CHECKLIST/FILE/VIDEO та
  підтримуваних MEASUREMENT/ANNOTATED_IMAGE блоків для картки й працівника.
- Фото завантажується через захищений file API та справді відображається.
  404 «Карти немає» відрізняється від 403, мережевої помилки чи 500.
- Мінімальний редактор техкарти: операції, текст, фото, попередження,
  чекліст, порядок; додавання, редагування і підтверджене видалення.
- Не будуй великий графічний редактор зараз. Збережи editable annotation
  source та версію схеми; існуючі анотації показуй, якщо вони підтримувані,
  і чесно повідомляй про непідтримуваний формат.
- Перевір цілісність перед затвердженням: валідний маршрут без циклів,
  потрібні операції/ролі та документи. Обов'язковість прошивки задається
  для конкретного виробу — не кожна антена потребує прошивки.

Перевір: працівник бачить фото розпайки, текст і галочки; може завантажити
правильну прошивку для своєї версії; копіювання версії переносить визначення;
зміна нової чернетки не змінює старі виробничі інструкції.
Коміт: `feat: робочі техкарти прошивки й маршрути`.

### Етап 7 — простий екран працівника і завершення ролей

- Вхід працівника веде в «Моя робота»: призначені або доступні операції.
- Поточна операція показує замовлення, виріб, комплектацію/версію,
  інструкцію, фото, потрібні файли й чекліст.
- Дії: «Почати», «Завершити», примітка, потрібне фото/вимірювання;
  кількісна робота завершується на фактично введену кількість.
- Сервер перевіряє роль, призначення, попередні етапи й обов'язкові докази.
- Помилка завантаження фото видима, прогрес не втрачається мовчки;
  незбережені відповіді захисти від випадкового виходу.
- Повтор запиту із тим самим ключем не збільшує кількість повторно;
  не створюй новий ключ для простого мережевого повтору тієї самої дії.
- Після виконання оновлюються виробничий прогрес і огляд замовлення.
- Не показуй працівнику недоступні редактори, ціни й управлінські дії.
  Приховування UI не замінює серверну авторизацію, включно з файлами.
- Дефекти/ремонт не імітуй текстовим статусом: їх повний процес відкладений.

Перевір реальні ролі: менеджер, закупівельник, інженер, складальник,
технік-електронік та інженер прошивок. QR веде до доступного виробу;
обхід URL не дає доступу до чужих/недозволених даних.
Коміт: `feat: зручна робота виробничих виконавців`.

### Етап 8 — узгоджена документація й перевірка наскрізного процесу

- Онови всі початкові статуси README/ARCHITECTURE/DATABASE/ROADMAP,

- Усунь зіпсоване кодування. Перевір UTF-8 і відсутність нульових символів.
- Наскрізний сценарій: результат розробки → продукція з двома
  комплектаціями → затверджена версія → замовлення → автоматична потреба →

Коміт: `docs: актуальний стан і перевірки оновленої BAZA`.

## 9. Перевірки і збереження після КОЖНОГО етапу

Не зберігай усю роботу одним фінальним комітом.

1. Онови docs/REWORK_PROGRESS.md: виконані задачі, зміни, міграції,
   фактичні перевірки, відкладені питання та наступний етап.
2. Виконай перевірки, передбачені AGENTS.md. Для змін даних/бізнес-логіки
   потрібні реальні PostgreSQL tests і migration checks; для UI — тести,
   ESLint, strict TypeScript/Vite build та browser verification.
   Після завершення фази — також чинні backend Ruff/package checks і
   Compose validation. Не пиши нові тести лише для повторення текстів/кольорів:
   перевіряй важливі сценарії й права.
3. Недоступну перевірку познач «Не виконано» з причиною. Проходження
   unit tests з mocked API не є доказом роботи реального backend.
   Якщо обов'язковий acceptance check заблокований, збережи checkpoint,
   познач етап незавершеним і не переходь до залежної зміни.
4. Перевір git diff і склад майбутнього коміту. Додавай явні файли етапу;
   не включай сторонні зміни, секрети, .env, бази, storage, node_modules,
   .venv та результати перевірок із конфіденційними даними.
5. Створи окремий коміт із повідомленням відповідного етапу.
6. Виконай push у ту саму гілку GitHub. Після першого коміту:

   ```bash
   git push -u origin refactor/baza-uk-orders
   ```

   Далі можна `git push`, коли upstream перевірено.
   Не використовуй force push, reset --hard або clean для обходу помилки.
   Для конфліктів не переписуй чужу історію; збережи checkpoint і поясни
   конкретний блокер. Паролі й токени не запитуй у тексті чату.
7. Перевір, що remote branch існує і її commit SHA збігається з локальним
   HEAD. Не називай локальний commit успішним збереженням на GitHub.
8. Покажи короткий звіт українською: що користувач тепер може зробити;
   виконані/невиконані перевірки; коміт; гілка; push успішний чи ні;
   що лишилося. Якщо push заблоковано — не приховуй це.

Не зливай гілку в main автоматично і не розгортай робочу систему:
поточна команда стосується роботи в окремій гілці зі збереженням на GitHub.
